## Overview

FishCount v1.0 was scoped as a 6-phase build (Ops Guardrails → Ingest → Browse + Picker + Trends → Forecasts → Email Alerts → Polish) targeting the core value statement *"given a date and a target species, help an angler pick the charter boat with the best historical odds."*

The first four phases shipped: a polite scraper writes to a canonical SQLite store via a strict DAL boundary, a SvelteKit read surface (`/`, `/picker`, `/boats/[id]`, `/compare`, `/trends`, `/about`) renders honest per-angler metrics with mandatory trip-type segmentation, and a statistical forecast layer (seasonal-naïve weighted-yield baseline + 80% prediction interval + n + 30-day horizon cap + n<5 refusal) powers calendar heatmap colouring on `/picker`.

The milestone closed early at the operator's direction following a deliberate scope pivot. The picker's "rank a boat for a target species" framing felt narrower than the explorer-style multi-axis trend view the operator decided they wanted instead. Phases 4 (Email Alerts) and 5 (Polish) were retired without execution and will be re-evaluated against the new core value in v2.

The integration audit (`v1.0-MILESTONE-AUDIT.md`) is the load-bearing record for everything that shipped, everything that didn't, and one known integration defect (the `/picker` rankings short-circuit hiding the Phase 3 heatmap for low-data future combos) that operator may or may not fix in v1 depending on whether the route survives the v2 redesign.

## Milestone Summary

**Key Decisions** (extracted from PROJECT.md and per-phase context):

- **Modular monolith over services** — one SvelteKit + adapter-node deployment, one SQLite database. Internal boundaries enforced by import discipline rather than process isolation.
- **DAL is the only module that issues SQL** — everything else (`lib/scraper/`, `lib/forecast/`, `src/routes/`) calls typed repositories in `lib/db/`. This boundary preserved the option to swap SQLite for Postgres later without touching domain code, and was enforced by a static-grep test.
- **Idempotent upsert on `(date, boat_id, trip_type, species)`** — re-running a scrape produces identical final state. Backfill = loop + `scrapeDate`. Parser-bug fixes = re-run affected dates.
- **All dates are `YYYY-MM-DD` in `America/Los_Angeles`** — a single `lib/shared/dates.ts` module is the sole producer of date strings, enforced by a static-grep test.
- **Phase 0 precedes Phase 1** — no scraping into the cloud without billing alerts, kill switch, dead-man's switch, and Litestream backups in place. Costliest rule retroactively to enforce.
- **Backfill is a CLI, not a cron route** — cron/function timeouts can't cover hours-long polite-rate-limited backfill. Implemented as resumable `npm run backfill` via `tsx`.
- **Pure-math forecast engine** — `compute.ts` follows `parser.ts` purity contract: no SQL, no module-scope `getDb`, db handle injected as parameter. Per-cell try/catch in `recomputeForecasts` means one bad cell never aborts the nightly recompute.
- **Forecast honesty: ship the baseline labeled, not a fake-fancy model** — seasonal-naïve fleet-mean weighted yield with 80% PI is the v1 forecast. `/about#forecasts` documents this transparently per CLAUDE.md non-negotiable #3.
- **Hybrid heatmap composer** — past cells from `heatmapForQuery` (catch_reports actuals) + today/future cells from `forecastHeatmapForQuery` (forecasts), merged by date. Tooltip discriminates via `'pi_low' in cell`.
- **Per-angler framing is structural, not cosmetic** — verbatim "derived boat-aggregate average, not individual angler" copy is rendered inline (not tooltip-only) on every page that shows a per-angler number, enforced by a 3-file allowlist lint test.
