# Phase 4 — UI Design Contract

> Visual and interaction contract for the only user-write surface in v1: email signup, double opt-in, manage-preferences, unsubscribe, and the four outbound email templates. Generated by gsd-ui-researcher in auto mode. Verified by gsd-ui-checker.

This contract inherits the Phase 2 visual system 1:1 — all tokens (`@theme` block in `src/app.css`), all components in `src/lib/components/`, the system-ui font stack, the 60/30/10 color split, the verbatim domain-language vocabulary, and every anti-feature guard. **Phase 4 adds zero new color tokens, zero new font sizes, and zero new spacing tokens.** New surfaces are composed from existing primitives.

What Phase 4 *does* add: new copywriting (signup CTA, validation errors, double-opt-in flow copy, email subject lines + body templates), new form-input primitives (honeypot, generic-success-on-suppressed flow), and email-specific rendering rules (table-based HTML for Gmail/Outlook compatibility, plain-text variants, mandatory compliance footer block).

The non-negotiables from `CLAUDE.md` rule #5 (double opt-in, suppression list, `List-Unsubscribe`, postal address, honeypot, disposable-email rejection, per-IP rate limit) are encoded as visual contracts here, not just backend rules. Compliance lives in the markup.

## Spacing Scale

Inherited verbatim from Phase 2. All values are multiples of 4.

| Token | Value | Tailwind | Phase 4 Usage |
|-------|-------|----------|---------------|
| xs | 4px | `1` | Honeypot field rendered at 0 width but with `padding: 4px` for screen-reader landmark detection (then `position: absolute; left: -9999px;`) |
| sm | 8px | `2` | Form-field label-to-input gap, inline error text top margin, badge inner padding |
| md | 16px | `4` | Form-field vertical gap, paragraph spacing in email body, card inner padding (mobile) |
| lg | 24px | `6` | Section padding, card inner padding (desktop), gap between form sections (e.g. "your email" vs "what you want to follow"), email-body margin between header and content |
| xl | 32px | `8` | Layout gaps between major page sections, gap between email content block and compliance footer |
| 2xl | 48px | `12` | Page-level top padding (desktop), gap above email signature block |
| 3xl | 64px | `16` | Top of /alerts hero block (desktop only); below `md:` only |

**Layout containers (web):** identical to Phase 2 — mobile `px-4 max-w-full`, tablet `sm:px-6`, desktop `md:px-8 max-w-6xl mx-auto`.

**Email body container:** fixed `max-width: 600px; margin: 0 auto; padding: 24px;` per the de-facto email-client standard. Outlook desktop renders ≤600px without horizontal scroll; Gmail caps display width at 600–650px on desktop and stacks to single-column on mobile via media queries.

**Touch targets (web forms):** every form input, submit button, checkbox, toggle, and unsubscribe link has a minimum hit area of 44×44px on mobile (`min-h-11` on `<button>` and `<input>`; checkboxes wrap their `<label>` so the entire 44px-tall row is the hit target).

**Email touch targets:** unsubscribe link in email footer is rendered at `padding: 12px 0;` line-height `24px` — gives ≥44px effective vertical hit area on mobile mail clients.

**Exceptions:**
- Honeypot input: `padding: 4px` is paired with `position: absolute; left: -9999px; opacity: 0; pointer-events: none; tabindex="-1"; autocomplete="off";` so the visual spacing token is never visible to humans but the field is reachable to robotic form-fillers that skip CSS.

## Typography

Inherited verbatim from Phase 2. Exactly 4 sizes, 2 weights (400 regular, 600 semibold). No italics. No 3+ font weights.

| Role | Size | Weight | Line Height | Tailwind | Phase 4 Usage |
|------|------|--------|-------------|----------|---------------|
| Body | 16px | 400 | 1.5 | `text-base font-normal leading-normal` | Form input text, page paragraphs, email body paragraphs, compliance-footer text |
| Label | 14px | 600 | 1.4 | `text-sm font-semibold leading-tight` | Form field labels ("Email", "Boats to follow"), inline error text, badge text, email subject-preview snippets |
| Heading | 20px | 600 | 1.25 | `text-xl font-semibold leading-tight` | Form section headings ("What do you want to follow?"), email body H2 ("Hot day on `[Boat Name]`"), preferences-page row labels |
| Display | 28px | 600 | 1.2 | `text-3xl font-semibold leading-tight md:text-4xl md:leading-tight` | Page titles ("Get fishing alerts", "Check your email", "You're confirmed", "Manage your alerts", "You're unsubscribed"), email H1 (rendered at 24px in email — see Email-specific overrides below) |

**Tabular numerals (web):** mandatory on every `n=X trips` label and per-angler value rendered inside an alert-preview block on the manage-preferences page. Implementation: `class="tabular-nums"` on the rendering element.

**Email-specific typography overrides:**
- Email H1: 24px / 600 / line-height 1.25 (not 28px — narrower 600px container needs smaller display).
- Email H2: 18px / 600 / line-height 1.3.
- Email body: 16px / 400 / line-height 1.5 (matches web).
- Email small print (compliance footer, "you're getting this because…"): 14px / 400 / line-height 1.5 / `color: #475569;` (—color-text-muted equivalent).
- All email font sizes declared inline on the rendering `<td>` or `<p>` element as `style="font-size: 16px; line-height: 1.5; ..."` — never via class. Email clients strip classes.
- Tabular numerals are NOT enforced in email (Outlook ignores `font-variant-numeric`); per-angler values in alert emails are rendered as plain text with the unit label adjacent.

**Decimal precision rule (CLAUDE.md non-negotiable #3 + #4 carried forward):** when a Phase 4 alert email displays a per-angler number (e.g. "today's catch: 4.5 fish/angler · n=18 anglers"), the `<PerAnglerMetric>` formatting rule applies — integer when ≥10, one-decimal when <10, never two decimals. The component cannot run inside email HTML (no Svelte runtime in Resend), so the *server-side email composer* (Plan 04 will name this) must apply the same formatting. This is not a UI choice; it's a contract.

**Accent reserved for (explicit list for Phase 4 — every other use of accent is a contract violation):**
1. Inherited from Phase 2: text links to internal routes, currently-active top-nav link, focus-visible ring.
2. Primary CTA buttons: "Subscribe to alerts" on `/alerts`, "Update preferences" on `/alerts/manage`, "Confirm subscription" button rendered inside the confirmation email.
3. Inline text links inside the "Why am I getting this email?" reason-for-receipt block (the boat or species name links back to the relevant FishCount page).
4. Email H1 text color (the email H1 uses accent so the brand is identifiable in mail-client previews).
5. The `✓` glyph on the email-confirmed success page (rendered as `text-(--color-accent)` Display-sized glyph above the heading).

**Accent is NOT for:**
- Inline validation errors → use `--color-destructive`.
- Honeypot-rejection / suppression-list-rejection feedback → there IS NO accented feedback for these; the page renders the same generic success state to avoid enumeration (anti-enumeration is a load-bearing UX rule — see `<SignupForm>` contract below).
- "Follow this boat" toggle in manage-preferences when *active* → use `--color-text` body weight + a small text "following" label, not an accent button.
- Disposable-email rejection → use `--color-destructive` with the inline-error pattern (different from honeypot/suppression which silently succeed).
- Email body text → body color only.
- The unsubscribe button in email footer → muted text + underline (NOT a CTA; deliberately understated to lower friction without being hidden).

### Color contrast (WCAG AA minimum, AAA where free) — Phase 4 additions

All Phase 2 contrast pairs continue to apply. Phase 4 adds these:

| Pair | Ratio | Compliance |
|------|-------|------------|
| `--color-destructive` on `--color-surface` (#b91c1c on #fff) | 7.1:1 | AAA |
| `--color-destructive` on `--color-surface-muted` (#b91c1c on #f8fafc) | 6.7:1 | AAA |
| `--color-text-muted` on email-footer surface `#f8fafc` (compliance-footer block) | 7.4:1 | AAA |
| Email H1 `--color-accent` on white (#1d4ed8 on #fff) | 8.6:1 | AAA |
| Email body `--color-text` on white | 18.7:1 | AAA |

**Email-client safety:** all colors are declared as raw hex values inline (`style="color: #1d4ed8;"`) when used in email HTML — `var(--color-*)` and Tailwind classes do not survive most email clients. The `@theme` block is web-only.

### Color-only state signaling (anti-pattern check)

Phase 4 must NOT signal state with color alone. Every state has at least two signals:

- **Validation error:** red border + `aria-invalid="true"` + visible error text adjacent to field + error icon glyph (`!` or `⚠`, FLAG: pick `!` to avoid the warning-yellow connotation of `⚠`). Three signals.
- **Honeypot triggered:** silently render generic success state (no signal at all to the bot — this is intentional). Server logs the event.
- **Suppression-list re-signup attempt:** silently render the same generic "check your email" success page as a fresh signup. No client-side signal that the address is suppressed (anti-enumeration). Three back-end signals (log, suppression-table updated_at, no email sent).
- **Email confirmation-pending → success transition:** the success page shows ✓ glyph + heading "You're confirmed" + body confirming what they signed up for. Three signals.
- **Unsubscribe success:** heading "You're unsubscribed" + body confirming the address + link back to `/`. Two signals (no green checkmark — staying neutral, since unsubscribe is a normal action, not a celebration).

### Heatmap palette

Not used by Phase 4. (No charts on form pages or email templates.) The 5 viridis stops in `@theme` remain reserved for Phases 2/3 surfaces.

## Copywriting Contract

**Voice:** SD angler audience, continuing Phase 2's tone. Knowledgeable, literal, direct. No marketing hype. No exclamation points (except in inline error glyph `!`). No emoji. Verbatim domain language carries over unchanged.

The compliance copy in this section is **load-bearing for legal and deliverability reasons**. Do not paraphrase, soften, or "improve" it without re-checking CAN-SPAM (15 U.S.C. § 7704), CASL §6(2), and GDPR Art. 7 / Art. 13. The wording below is checked against those statutes for v1.

All Phase 2 verbatim strings (trip types, landings, species, "fish/angler", "n=X trips") apply to Phase 4 surfaces unchanged. The signup form's "boats to follow" and "species to follow" controls render the same verbatim labels as Phase 2 filter selects — pulled from the same source.

### Form-field labels and placeholders (`<SignupForm>`)

All labels are above the input (not floating, not inside). All placeholders are example values, never instructions (instructions go in helper text below the input).

| Field | Label | Helper text | Placeholder | Required |
|-------|-------|-------------|-------------|----------|
| Email | "Email address" | "We'll send a verification link before activating any alerts." | "you@example.com" | Yes (asterisk: `<span aria-hidden="true" class="text-(--color-text)">*</span>` — note: NOT destructive-color, FLAG resolved per Phase 2 FLAG #2) |
| Boats to follow | "Boats to follow (optional)" | "Pick the boats you want catch alerts for. Leave blank to follow species only." | (multi-select, no placeholder) | No |
| Species to follow | "Species to follow (optional)" | "Pick the species you want run-start alerts for." | (multi-select, no placeholder) | No (but at least one of boats OR species must be selected — see validation) |
| Honeypot | (visually hidden — see below) | (none) | (none) | (must be empty for submission to be accepted; if non-empty, render generic success and discard server-side) |

**Honeypot field markup contract:**
```html
<div class="absolute left-[-9999px] h-0 w-0 overflow-hidden" aria-hidden="true">
  <label for="website">Leave this field blank</label>
  <input
    type="text"
    id="website"
    name="website"
    tabindex="-1"
    autocomplete="off"
    value=""
  />
</div>
```
- Field name is `website` — common-enough to attract dumb bots, never a real signup field for FishCount.
- `aria-hidden="true"` and `tabindex="-1"` keep it out of screen-reader and keyboard tab order.
- `autocomplete="off"` prevents browser password managers from filling it.
- Server treats `website !== ""` as a bot signal: render generic success, log + count, send no email.

**Optional-fields constraint:** if both `boats` and `species` arrays are empty on submit, render an inline validation error: "Pick at least one boat or species to follow." This is a destructive-color inline error (the only deliberate user-facing form error besides disposable-email rejection).

### Validation error states (inline, per-field)

| Trigger | Error copy | Visual |
|---------|------------|--------|
| Empty email | "Email is required." | Red border on input + red text below + `!` glyph |
| Malformed email syntax | "That doesn't look like a valid email address." | Red border + red text + `!` |
| Disposable-email domain detected (server-side check) | "We can't send to disposable addresses. Use a permanent inbox so you don't lose your unsubscribe link." | Red border + red text + `!` |
| No boats AND no species selected | "Pick at least one boat or species to follow." | Red text below the multi-selects + `!` glyph (no border on the selects, since both are valid individually — the error is on the pair) |
| Per-IP rate limit exceeded (≥4 signups from same IP in 1h) | "We've gotten a lot of signups from your network. Try again in an hour, or [contact us](mailto:contact@fishcount.example)." | Renders as a page-level error block above the form (not an inline-field error), red text on white background, `!` glyph |
| Honeypot field non-empty | (no user-visible error — silently render generic success page) | (none) |
| Address is in suppression list | (no user-visible error — silently render generic success page; do NOT send confirmation email) | (none — anti-enumeration) |

**Anti-enumeration rule (load-bearing):** The honeypot-triggered and suppression-list cases MUST render the exact same `/alerts/pending` "Check your email" page as a successful first-time signup. The user/bot cannot tell from the page response whether their address was already suppressed or whether the honeypot rejected them. This prevents an attacker from probing which addresses are already in the suppression list. Server logs distinguish; UI does not.

### Generic success page `/alerts/pending`

Heading: **"Check your email"**

Body (verbatim):
```
We sent a verification link to [user-entered email, masked: f***@d***.com — see masking rule below].

Click the link in that email within 24 hours to activate your alerts. If you don't see it,
check your spam folder.

You're not subscribed to anything yet. Activation only happens after you click the link.
```

**Email masking rule for display:** show the first character of the local part, then `***`, then `@`, then the first character of the domain, `***`, then the TLD. So `kaikai.liu@gmail.com` renders as `k***@g***.com`. This avoids displaying a misspelled address back at the user (which would be confusing) AND avoids confirming the exact address back to a bot (small enumeration mitigation).

**Why "you're not subscribed yet" is mandatory:** double-opt-in compliance + prevents users from thinking they've opted in when they haven't (CAN-SPAM transparency).

### Confirmation success page `/alerts/confirmed`

Heading: **"You're confirmed"** (with `✓` glyph above, accent color, Display size).

Body (verbatim, with template variables):
```
You're now subscribed to:
  · [list of followed boats, verbatim names]
  · [list of followed species, verbatim names]

We'll email you when:
  · A boat you follow has a "hot day" (today's avg/angler > 2× its trailing 30-day same-trip-type average, with ≥ N anglers).
  · A species you follow has a "starting to run" signal (rolling 7-day fleet-wide avg > 1.5× same-week-last-year baseline).

You can [manage your alerts](/alerts/manage?token=[signed]) or unsubscribe anytime from any email.
```

The "hot day" and "starting to run" definitions are rendered verbatim because the user needs to know the trigger thresholds. This is part of the "honest forecasting" framing (CLAUDE.md non-negotiable #3) extended to alerts.

### Manage-preferences page `/alerts/manage?token=[signed]`

Heading: **"Manage your alerts"**
Subtitle: "Subscribed as `[user email, fully visible — they're authenticated via the signed token]`"

Sections:
1. **Followed boats** — list of currently-followed boats, each with a "Remove" text link (muted color). Below the list: a multi-select to add new boats (same control as signup).
2. **Followed species** — same shape as boats.
3. **Pause alerts** — a checkbox: "Pause all alerts for [duration select: 1 week / 2 weeks / 1 month / until I turn back on]". State persisted on the subscriber row, read by alert dispatcher.
4. **Update preferences** button (accent, primary CTA at bottom).
5. **Unsubscribe from all** text link (muted, separate row below the button) — links to `/alerts/unsubscribe?token=[signed]`.

If the token is invalid or expired:
- Heading: "This link is no longer valid"
- Body: "Magic links expire after 30 days. Sign up again to get a fresh link." + CTA "[Sign up again](/alerts)" (accent).
- DO NOT reveal whether the email exists in the database — same anti-enumeration discipline as signup.

### Unsubscribe page `/alerts/unsubscribe?token=[signed]`

**This page MUST work without JavaScript** (CAN-SPAM "one-click unsubscribe" + RFC 8058 List-Unsubscribe-Post requirement). The handler is a server endpoint that performs the suppression-list write on GET (or POST from the List-Unsubscribe-Post header) and renders a confirmation page.

Heading: **"You're unsubscribed"**
Body (verbatim):
```
We've removed [user email, masked: k***@g***.com] from all FishCount alerts.

You won't receive any more emails from us. If you change your mind in the future, you'll need
to sign up with a different email address — once an address unsubscribes, we don't reuse it.

[Back to FishCount](/)
```

**Critical anti-feature:** there is NO "are you sure?" interstitial. One-click unsubscribe is one click — the link in the email goes directly to this confirmation page after the server has already written to the suppression table. RFC 8058 compliance and one-click are the same requirement.

**Token-invalid case:** if the token can't be verified, render: "This unsubscribe link is no longer valid. [Contact us](mailto:contact@fishcount.example) and we'll handle it manually." This is the only contact-pointer in Phase 4 — Phase 5 polish (POL-02) will populate the contact email globally.

### Inline framing for "follow this" CTAs (carried-forward credibility discipline)

Per CLAUDE.md non-negotiable #4 (per-angler framing), the inline "Get alerts for this boat" CTA on `/boats/[id]` and the "Get alerts when this picks up" link on `/picker` MUST appear after the per-angler metric is already rendered with its `derived boat-aggregate average` framing. They must NOT replace or substitute for that framing. Phase 2's `<PerAnglerFramingProvider>` continues to fire on these pages; the alert CTAs are additive UI, not a credibility shortcut.

### Email subject lines (deliverability + clarity)

Subject lines are short (≤50 chars to render fully on iOS Mail and Gmail mobile previews), avoid spam-trigger words ("FREE", "ACT NOW", "!!!"), and use sentence case. Verbatim domain language wins.

| Email | Subject | Preheader (preview text) |
|-------|---------|-------------------------|
| Confirmation | "Confirm your FishCount alerts" | "One click to activate. We won't email until you do." |
| Hot-day alert | "Hot day: [Boat Name]" | "[N] fish/angler today on [trip_type] — [Nx] above its 30-day average." |
| Starting-to-run alert | "[species] starting to run" | "Fleet-wide 7-day avg is [Nx] above same-week last year on [trip_type] trips." |
| Generic admin (rare — preference confirmation, etc.) | "Your FishCount preferences" | "[plain summary of what changed]" |

The preheader (a hidden `<div>` at the top of the email body, ≤90 chars, hidden in the body via `display: none; max-height: 0; overflow: hidden;`) controls what mobile mail clients show in the inbox preview. Without it, clients pick the first line of body text — which we don't want to be the unsubscribe link.

### Email body structure (every alert email — mandatory blocks in this order)

**Block 1: Hidden preheader** (see above).

**Block 2: Brand header** — single line, accent color: "FishCount" (text-only logo, no image — image-blocked clients show nothing).

**Block 3: H1** — the alert's purpose:
- Confirmation: "Confirm your alerts"
- Hot day: "Hot day on [Boat Name]"
- Starting to run: "[species] is starting to run"

**Block 4: Body content** — short paragraphs (no walls of text):
- Confirmation email: "Click the button below to confirm your subscription. The link expires in 24 hours. If you didn't sign up, ignore this email — your address won't be added to anything." + button "Confirm subscription" (accent, table-based for Outlook).
- Hot-day alert: "Today on [Boat Name] ([trip_type]): [PerAnglerMetric value] · n=[anglers] anglers. That's [Nx] above its trailing 30-day same-trip-type average." + link "View [Boat Name] on FishCount → [/boats/[id]]"
- Starting-to-run alert: "[species] rolling 7-day fleet-wide avg on [trip_type] is now [Nx] above same-week last year." + link "View [species] trends → [/trends?species=…]"

**Block 5: "Why am I getting this email?" reason-for-receipt block** — gray background (`#f8fafc`), 14px text, full-width:
- Confirmation: "You're getting this because you signed up at fishcount.app/alerts on `[YYYY-MM-DD]` from IP `[masked IP, e.g. 73.x.x.x]`. If that wasn't you, ignore this email."
- Hot-day / starting-to-run: "You're getting this because you followed [Boat Name / species] on fishcount.app on `[YYYY-MM-DD]`. [Manage alerts](/alerts/manage?token=…) · [Unsubscribe](/alerts/unsubscribe?token=…)"

**Block 6: Compliance footer** — gray background, 14px muted text, separate from reason-for-receipt by a 32px gap:
```
FishCount · Public San Diego charter-boat dock-totals aggregator
[Physical postal address — POPULATED IN PLAN 04 — must be a real mailing address before first send]

Unsubscribe: [one-click link, accent color, underlined]
```

**Block 7: List-Unsubscribe header** — set on every outbound email at the SMTP/Resend layer:
```
List-Unsubscribe: <mailto:unsubscribe+[token]@fishcount.example>, <https://fishcount.app/alerts/unsubscribe?token=[signed]>
List-Unsubscribe-Post: List-Unsubscribe=One-Click
```
Both endpoints (mailto and HTTPS) MUST work and write to the suppression table.

### Plain-text email variants (mandatory)

Every email MUST be sent as multipart/alternative with a plain-text variant. Spam filters score lower on multipart/alternative; some users (and most CLI mail clients) read plain text only.

The plain-text variant follows the same block structure but renders without HTML:
- Brand header → "FishCount"
- H1 → uppercase or surrounded by `===`
- Body → wrapped at 72 chars
- Reason-for-receipt → prefixed by `--- Why am I getting this email? ---`
- Compliance footer → prefixed by `--`
- Unsubscribe link → bare URL on its own line: "Unsubscribe: https://fishcount.app/alerts/unsubscribe?token=…"

Both variants MUST contain the postal address and the unsubscribe link verbatim. CAN-SPAM compliance is per-variant.

### Ramp-up / warm-up disclosure (ALT-12)

During the first two weeks of production sending, a banner appears on `/alerts` (the signup page) ABOVE the form:

```
Note: we're warming up our email sender — alerts during the first two weeks are
limited to 50/day (week 1) and 200/day (week 2). If volume exceeds the cap, alerts
queue and send the next morning. We never silently drop alerts.
```

Visual: amber `--color-provisional-bg` background, amber-700 text, `<svg>`-free, dismissable but stored in localStorage so it doesn't reappear after dismiss. After the warm-up window expires (controlled by an env var or a date constant), the banner stops rendering.

This is NOT marketing copy. It's an honesty disclosure — the user might submit an email and not get an alert that fires for someone else 30 minutes later because they're #51 in the queue. Telling them up front is the credibility-guardrail co-shipping pattern from CLAUDE.md.

- The component cannot render WITHOUT the honeypot. Throws in dev if removed.

### 3. `<EmailLayout>` — `src/lib/email/EmailLayout.ts` (server-only HTML builder)

Server-side function (NOT a Svelte component — Resend templates are HTML strings) that wraps email content blocks in the table-based 600px container with proper inline styles.

**Signature:**
```ts

  subject: string;       // for List-Unsubscribe headers + Resend metadata
  preheader: string;
  h1: string;
  bodyHtml: string;      // pre-rendered content block(s) — plain HTML, no Svelte

```

Returns BOTH variants. Plain-text generation is mechanical: strip tags, wrap at 72 chars, render links as `[text](url)` then bare URL on its own line.

**Required inline styles (per cell):**
- `font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif;`

**Outlook-specific safeguards:**
- The CTA button is a `<table>` (not `<a class="button">`), with `<v:roundrect>` MSO conditional fallback for Outlook desktop's rounded corners.
- No background-image on any cell (Outlook 2007–2019 fails on these silently).
- Width is set as both `width="600"` attribute and `style="width: 600px;"` (Outlook reads attribute, others read style).

### 4. `<ComplianceFooter>` (renders inside `<EmailLayout>`, not a separate file)

Single source of truth for the postal address + unsubscribe block. Specified as a string-template inside `EmailLayout.ts`. The block must always render in this exact order:

1. "FishCount · Public San Diego charter-boat dock-totals aggregator" (Brand line, body color)
2. Postal address (one line, body color, muted)
3. Empty line (32px gap)
4. "Unsubscribe: [one-click link, underlined, accent color]"

Address sourcing: a single `POSTAL_ADDRESS` environment variable read at email-build time. If empty or unset, **email send fails closed** — the email composer throws and the alert dispatcher logs to the operator-alert pipeline. Better to silently drop a single alert than to send a non-compliant email.

## Interaction Contracts

### Signup form submission (`/alerts`)

1. User fills email + at least one boat or species.
2. Client-side validation: email syntax, "at least one of boats or species selected." If fail, render inline error, do NOT submit.
3. Submit via `fetch('/alerts', { method: 'POST', body: FormData })`.
4. Server checks (in order):
   a. **Honeypot** — if `website` field is non-empty: render generic success page, log, send no email.
   b. **Per-IP rate limit** — if 4th signup from same IP within 1h: render page-level rate-limit error, send no email.
   c. **Disposable-email domain** — if matched against block-list: render inline disposable-email error.
   d. **Suppression list lookup** — if email already suppressed: render generic success page (anti-enumeration), send no email.
   e. **Already-pending lookup** — if email has a pending confirmation token <24h old: render generic success page, do NOT send a second confirmation email (avoids confirmation-spam flood).
   f. **Active-subscription lookup** — if email is already an active subscriber: render `/alerts/confirmed` directly with the existing preferences, do NOT send a confirmation email.
   g. **Happy path** — write pending row, send confirmation email, render generic success page.
5. Generic success page (`/alerts/pending`) shows masked email so user can verify they typed correctly without exposing exact address.

### Confirmation link click

1. User clicks the link in the confirmation email — URL is `/alerts/confirm?token=[signed]`.
2. Server verifies the signed token (HMAC over `email + nonce + expires_at` with project secret).
3. If valid + not expired: write the active-subscription row, mark the pending row as confirmed, render `/alerts/confirmed` with subscription summary.
4. If invalid or expired: render `/alerts/confirmed` shell with content replaced by "This link is no longer valid…"
5. NO JavaScript required at any step.

### Manage-preferences interactions

- "Remove" link on a `<PreferenceRow>`: server-side form POST → write to subscription table → re-render the page.
- "Update preferences" button: submits the multi-selects → server diffs current vs new → applies diff → re-renders the page with a green-text confirmation message at top: "Preferences updated."
- Changes do NOT trigger a confirmation email (that would be email-spam-prone and irritating).

### Unsubscribe (one-click)

- GET `/alerts/unsubscribe?token=[signed]` (from email link click) OR POST to same URL (from List-Unsubscribe-Post mail-client one-click) → server writes to suppression table → renders confirmation page.
- NO interstitial. NO "are you sure?". NO JS required.
- Token signature is HMAC over `email + 'unsubscribe' + project_secret` with no expires_at — unsubscribe links never expire.

### Inline "Get alerts" CTA on `/boats/[id]` and `/picker`

- Click → navigate to `/alerts?boat=[id]` or `/alerts?species=[name]` (signup form pre-fills the multi-select).
- This is a navigation, not an inline form. Keeps the boat/picker pages free of form-state ambiguity.

## Accessibility

### Keyboard navigation

All Phase 2 contracts apply. Phase 4 additions:

- Form tab order on `/alerts`: warm-up banner dismiss button (if present) → email input → boat multi-select → species multi-select → submit button. (Honeypot is skipped via `tabindex="-1"`.)
- Form tab order on `/alerts/manage`: each PreferenceRow's "Remove" link → boats multi-select → species multi-select → "Update preferences" button → "Unsubscribe from all" link.
- Validation errors are announced via `role="alert"` / `aria-live="polite"` on the inline-error spans. Screen readers hear the error within ~1s of submit.
- The submit button uses `aria-busy="true"` during submission so screen readers announce "Submitting…" instead of leaving the user in silence.

### Screen readers

- Every form input has an associated `<label for="…">` or wrapping `<label>`.
- Every input has helper text via `aria-describedby` pointing at the helper `<p>`.
- The honeypot field has `aria-hidden="true"` so screen readers ignore it.
- Email-masking on the success page (`k***@g***.com`) is announced literally — acceptable; the masking is a privacy feature.
- The `✓` glyph on `/alerts/confirmed` has `aria-hidden="true"` — the visible "You're confirmed" heading carries the meaning.

### Email accessibility

- All alert emails use semantic HTML: `<h1>`, `<h2>`, `<p>`, `<a>`. No `<div>`-soup layouts where avoidable. (Outlook still requires table-based layout for some compatibility but content elements remain semantic.)
- Every `<a>` has visible link text describing the destination ("View [Boat Name] on FishCount →"), never "click here."
- Color is not the only signal: the unsubscribe link is underlined AND in accent color.
- Plain-text variant is the universal accessibility fallback.

### No color-only state signaling

(See "Color → Color-only state signaling" above.) Every state in Phase 4 has at least two signals (text + color, glyph + text + color, etc.).

### Reduced motion

Phase 2's `prefers-reduced-motion: reduce` rule covers Phase 4's web pages. Email animations: NONE. Email clients largely strip CSS animation; we don't ship any.

### Touch targets

- All form inputs: `min-h-11` (44px).
- Email CTA buttons: 44px minimum line-height in the table cell.
- Email unsubscribe link: 24px line-height with 12px vertical padding = 48px effective hit area.

## Anti-Feature Guards (UI patterns this phase REFUSES to render)

All Phase 2 anti-features carry forward unchanged. Phase 4 adds:

1. **No "are you sure?" interstitial on unsubscribe.** One-click means one click. (RFC 8058 + CAN-SPAM.)
2. **No win-back / re-engagement emails to suppressed addresses.** Once an address is in the suppression list, no email is ever sent to it again — including "we miss you" emails. The suppression table cannot be re-subscribed from the public form (ALT-06).
3. **No A/B testing of subject lines or send-time optimization in v1.** v1 ships one subject per email type. (Avoids the temptation to drift into engagement-bait copywriting.)
4. **No "ON FIRE", "🔥", "HOT BITE" in any alert subject or body.** "Hot day" is the verbatim alert name (it's what the trigger is called in the codebase) — but the subject line is "Hot day: [Boat Name]" with no flame emoji, no ALL CAPS, no exclamation point.
5. **No tracking pixels.** No open-tracking. No click-tracking. (Resend offers these — we DISABLE them in the API call.) FishCount does not have analytics; we don't surveil the recipients.
6. **No "your friend signed you up" / referral-signup flows.** The signup form is anonymous and self-service only.
7. **No SMS / push opt-in upsell on the signup page.** Email only in v1 (CLAUDE.md anti-feature: "push/SMS (v1)").
8. **No social-share CTAs in alert emails.** ("Share this hot day on Twitter!") Out-of-scope per anti-features list.
9. **No image-based content blocks in emails.** Image-blocked clients (default in Outlook 2007–2019) would render a blank email. Logo is text-only.
10. **No HTML form inside an email.** (Some clients support it via AMP for Email; we don't use it. Adds attack surface and AMP-specific compliance complexity for zero v1 value.)
11. **No "Are you a robot?" CAPTCHA on signup.** v1 uses honeypot + rate-limit + disposable-email-rejection (ALT-03/04). Adding CAPTCHA is a UX hit and unnecessary at v1 traffic volume.
12. **No phone number / location collection on signup.** Email + boats + species. Nothing else.
13. **No "Share your fishing photos" account-creation upsell anywhere.** Anti-feature per CLAUDE.md.
14. **No mid-email interstitial / sponsored content in alert emails.** Alert content is exactly what the alert is for. No "while you're here" promos.
15. **No "Manage" link without a signed token.** The manage page MUST be reached via a signed magic link, never via a plain `/alerts/manage` URL. Same for unsubscribe.
16. **No exposing whether an email exists.** Both the signup endpoint (suppression-list re-attempts) and the manage endpoint (invalid token vs. expired token) render identical responses. Anti-enumeration is load-bearing.

## FLAGs (genuinely 50/50 design choices, recorded for revisit)

These are choices made under auto mode where reasonable defaults were picked but the planner / executor may revisit during implementation:

1. **"Alerts" entry in top nav:** omitted in Phase 4. Discoverability is via inline CTAs on boat/picker pages. Phase 5 polish may add a top-nav entry. (Inherits Phase 2 FLAG #9 spirit.)
2. **Required-field asterisk color in `<SignupForm>`:** resolved to `--color-text` (NOT destructive-color) per Phase 2 FLAG #2. This is the first phase to make the call live; if checker objects, switch back to destructive.
3. **Multi-select control for boats/species:** native `<select multiple size="8">` for v1. Phase 5 may upgrade to a chip/pill picker. (Inherits Phase 2 FLAG #5.)
4. **Confirmation-email CTA button width:** 200px fixed. Some mobile mail clients render < 320px wide and might want full-width — measured trade-off; 200px reads as a button rather than a banner.
5. **Email H1 color:** accent (`#1d4ed8`). Some senders prefer body-color H1 for tone-down. Accent gives brand recognition in image-blocked previews; we keep it.
6. **Manage-preferences pause-alerts feature:** included in v1. Could be deferred to Phase 5. Including it because it's a load-bearing alternative to unsubscribe (some users want to silence during off-season without losing their subscription) and because suppression-list-permanence makes "just unsubscribe and re-up later" not work.
7. **Generic preference-confirmation email (Email 4):** v1 omits it. Manage-page in-line success message is sufficient. Re-evaluate if user feedback requests it.
8. **Banner dismissal persistence:** the warm-up banner dismiss state is stored in localStorage. Some users browse with localStorage disabled; for them the banner re-renders on every visit. Acceptable for a 2-week window.
9. **Email rendering of `<PerAnglerMetric>`-formatted values:** server-side composer in `EmailLayout.ts` re-implements the formatter. Risk: the two formatters can drift. Mitigation: a single shared `formatPerAngler(value, nTrips)` function in `src/lib/shared/format.ts` consumed by both Svelte component and email composer.
10. **Postal address sourcing:** env var `POSTAL_ADDRESS`. If a maildrop / virtual mailbox service hasn't been chosen by Phase 4 plan-time, the planner blocks the phase until one is procured. The address MUST be real before first send (CAN-SPAM).
11. **Honeypot field name:** `website`. Could be `phone` or `address` or randomized. `website` chosen because dumb auto-fillers commonly target it and it's not present elsewhere on the form (so a non-empty value is unambiguously a bot).
12. **Per-IP rate-limit window:** RESOLVED 2026-04-28: 3/h matches REQUIREMENTS.md ALT-03 verbatim. Could be tightened further if abuse observed. (Earlier draft proposed 4/h matching "rejects a fourth submission" wording — overridden in favor of REQUIREMENTS.md's explicit "3 signups per hour per IP".)
