# Phase 0 Plan 01: Litestream Replication Summary

**Continuous SQLite → Backblaze B2 replication via Litestream 0.3.13 wrapping Node as PID 1, with restore-on-boot, a first-boot-safe flag pair, a smoke-test DAL to prove replication end-to-end, and two operator-run verification scripts.**

## Accomplishments

- Litestream is now baked into the Docker image via a dedicated alpine builder stage that downloads the v0.3.13 linux-amd64 release tarball. The binary is promoted into the runtime image at `/usr/local/bin/litestream`, alongside `/etc/litestream.yml` and the rewritten `/usr/local/bin/entrypoint.sh`.
- `scripts/entrypoint.sh` now does two things before Node starts: (1) `litestream restore -if-db-not-exists -if-replica-exists -config /etc/litestream.yml "$DB_PATH"` — idempotent, first-boot-safe; (2) `exec litestream replicate -config /etc/litestream.yml -exec "node build/index.js"` — Litestream becomes PID 1 and supervises Node as its child process.
- `litestream.yml` points at `${DB_PATH}` with an S3-type replica targeting Backblaze B2 via `force-path-style: true`. Retention is 720h (30 days of WAL) with a 24h snapshot interval. All four credential/config fields (`LITESTREAM_ACCESS_KEY_ID`, `LITESTREAM_SECRET_ACCESS_KEY`, `LITESTREAM_BUCKET`, `LITESTREAM_ENDPOINT`) are `${ENV_VAR}` placeholders that Litestream expands from Fly secrets at runtime.
- `src/lib/db/smoke.ts` is the sole SQL-issuing module in Phase 0 (CLAUDE.md Architecture Rule). It exports `openSmokeDb`, `writeSmokeRow`, `readSmokeRows`, `countSmokeRows` against a single `smoke_test` table in WAL mode with `synchronous = NORMAL`. Phase 1 will delete this file and replace it with the real catch_reports / boats / landings / scrape_runs repositories.
- `better-sqlite3@12.9.0` + `@types/better-sqlite3@7.6.12` installed. `npm run build` passes cleanly; `build/index.js` is produced (confirmed).
- `scripts/verify-replication.sh` — operator-run. Writes a unique marker row inside the deployed Fly machine, waits 20s, then executes Check A (`fly ssh console -C "litestream replicas"`) and Check B (`b2 ls b2://fishcount-backup/fishcount.sqlite3/`) per 00-RESEARCH.md §Q4.
- `scripts/restore-drill.sh` — operator-run, destructive, explicit ack required. Writes a marker, flushes, deletes `/data/fishcount.sqlite3` + WAL + SHM siblings, restarts the machine, and confirms the marker round-trips after the entrypoint's restore branch runs.
- `docs/ops-litestream.md` — operator runbook covering daily checks, DR (both volume-loss and bucket-compromise paths), known landmines (missing `-if-replica-exists`, overly broad B2 key scope, retention/snapshot trade-offs), and the documented/accepted <1s sync-window write-loss risk for Phase 0.

## Decisions Made

- **Verbatim copy of 00-RESEARCH.md §Q4 Dockerfile + entrypoint + litestream.yml.** The plan explicitly requires this; the linkding-on-fly pattern is production-verified on Fly.io and we gain nothing by re-styling it.
- **Both safe-flag pair mandatory on restore.** `-if-db-not-exists` AND `-if-replica-exists`. The acceptance criteria grep for the exact combined substring; Pitfall 1 in 00-RESEARCH.md calls out the boot crash loop that results from omitting `-if-replica-exists`.
- **src/lib/db/smoke.ts is the entire Phase 0 DAL.** CLAUDE.md's "DAL is the only module that issues SQL" rule applies now, not after Phase 1. One file, one table, one purpose: prove replication + restore end-to-end before any real data lands.
- **Accept Phase 0 <1s sync-window risk.** Documented in the runbook. Phase 1 will add `litestream wait -path $DB_PATH` after critical scrape writes. There is no real data yet to lose.

## User Setup Required

This plan depends on Backblaze B2 + Fly secrets configured by the operator before Plan 06 can deploy. Per `00-01-PLAN.md` frontmatter `user_setup`:

1. **Backblaze account** at <https://www.backblaze.com/sign-up/cloud-storage> (free tier; card required for signup but no charge under 10 GB).
2. **Create a private bucket** named `fishcount-backup` (Private — the default — never Public; T-01-01 threat).
3. **Create an application key scoped to `fishcount-backup` only** (never the master key; T-01-02 threat), with Read + Write permission.
4. **Copy the keyID and applicationKey** — they are shown once.
5. **Set Fly secrets** (do NOT put these in `fly.toml [env]` — T-01-03 threat):
   - `LITESTREAM_ACCESS_KEY_ID` ← B2 application keyID
   - `LITESTREAM_SECRET_ACCESS_KEY` ← B2 application applicationKey
   - `LITESTREAM_BUCKET=fishcount-backup`
   - `LITESTREAM_ENDPOINT=s3.us-west-000.backblazeb2.com` (varies by bucket region; read the exact value from the B2 bucket "Endpoint" field)
